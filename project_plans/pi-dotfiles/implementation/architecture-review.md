## Concerns

- **Story 1.2.1 / Task 1.2.1a — cross-module gate parked inside the wrong module.** `verify_pinned_sources_reviewed()` cross-references two aggregates — the rendered `packages`/`extensions` output of `PiConfigSource` (`stapler-scripts/llm-sync/src/sources/pi_config.py`) and `ExtensionManifestSource`'s registry — but the plan places it inside `extension_manifest.py`, whose other responsibility (Epic 1.1) is narrowly "parse the manifest file's own schema." That forces `extension_manifest.py` to import `LoadedPiConfig`/`PiConfigError` from a sibling source module to do a job that isn't manifest parsing. **Remediation**: extract the gate into its own module (e.g. `src/sources/review_gate.py`) or a thin function in `cli.py` that composes both sources' outputs, leaving `extension_manifest.py` scoped to manifest schema/parsing only.

- **Story 4.1.1 — an AC that no test can actually verify.** The AC states the manifest entry's `notes` field must record specific findings ("not a placeholder like 'reviewed, looks fine'") and phrases this as Given/When/Then, implying it's checkable. No code can distinguish genuine security-review findings from eloquent boilerplate — this is a human-judgment criterion dressed as an executable one, which cuts against the plan's own stated philosophy ("the preferred fix... is executable validation, not prose"). **Remediation**: reframe as a manual-review checklist item (already covered by Epic 1.4's seven-step skill) rather than a testable AC; at most, add a narrow keyword/length smell-check that is explicitly documented as a weak heuristic, not a substitute for review.

- **Lens 2 / Reuse Check — pinned-fork-source parsing will be duplicated, not reused.** `PiConfigSource._is_allowed_package_source` ([`pi_config.py:178-198`](file:///home/tstapler/dotfiles/stapler-scripts/llm-sync/src/sources/pi_config.py#L178-L198)) already parses `git:github.com/tstapler/<repo>@<commit>`-shaped strings (splitting on the trailing `@`, validating the commit-hex shape, checking the `tstapler`-owned-fork substring). `verify_pinned_sources_reviewed()` (Task 1.2.1a) must independently re-derive repo+commit from the same rendered source strings to cross-check against the manifest. The plan defines no shared `Pin`/`SourceRef`/parser used by both, so the two checks can silently drift (e.g. if the fork-URL shape is loosened in one and not the other) — exactly the copy-pasted-validation failure mode `code-architecture-best-practices`' Reuse Check calls out as the highest-value thing to catch before writing new logic. **Remediation**: extract a shared `parse_fork_source(source: str) -> ForkSource(repo, commit)` (or equivalent) used by both `_is_allowed_package_source` and the new gate.

- **Story 1.1.2 — "illegal states unrepresentable" is implemented as a runtime check, not a type-level guarantee, and the invariant gets re-checked twice.** The plan's AC ("approved entry with no `approved_by` is rejected... raises `ManifestError`") is enforced in `ExtensionManifestSource.load()` per Task 1.1.2a — i.e. Parse-don't-Validate at the *file* boundary, which is good, but `ManifestEntry` itself (a flat frozen dataclass, Task 1.1.1b) has no invariant of its own: nothing stops `ManifestEntry(disposition="approved", approved_by=None)` from being constructed directly by other code (e.g. `fork_pin_extension.py`'s scaffold-writing, or a test) that doesn't route through `.load()`. Consequently `verify_pinned_sources_reviewed()` (Story 1.2.1) must separately re-check `disposition == "approved"` at gate time — the same invariant proven once by `load()` and re-validated again at the gate, the "Validate" anti-pattern `type-driven-design`'s Technique 1 warns against, rather than the type carrying the proof. This is the gate that decides whether a third-party fork is allowed to render — worth getting right. **Remediation (cheap)**: move the check into `ManifestEntry.__post_init__` so construction itself enforces the invariant regardless of call site. **Remediation (stronger)**: split into a `CandidateEntry`/`ApprovedEntry` sum type (Technique 3) so `approved_by: str` is simply not a field `CandidateEntry` has.

- **ADR-002 / Pattern Decisions table — "Adapter" mislabels what Epic 4.1 actually builds.** ADR-002 and the plan's Pattern Decisions table call the `pi-1password` integration a GoF Adapter "around Pi's existing `packages`/`extensions` registry mechanism." But Epic 4.1's own Files list (`.config/pi/extensions-manifest.json`, the ADR doc) shows no adapter class is written — the extension is registered exactly like every other opt-in `packages` entry (disabled by default), the same Registry/Feature-Toggle mechanism the same table uses, correctly, for the permission system, plan mode, and the compat shim. There is no interface translation happening for a future reader to find. **Remediation**: relabel as "Registry entry, disabled by default — same mechanism as the other opt-in packages in this table," matching what's actually implemented.

- **Story 2.2.1 — two independent, non-transactional ledger writes from one config snapshot, with no test for the interrupted case.** `PiSettingsTarget.save()` and `PiPackageLedger.save()` are both driven from the same `LoadedPiConfig` but are sequenced, separately-atomic writes (Task 2.2.1b: ledger save happens "after a successful settings write"). None of the three GWT tests in Story 2.2.1 cover a process interrupted between the two writes. Working through it: the skew is self-healing (next idempotent run reconciles both) and safe in the failure direction (`prune` only deletes what the ledger already tracks, so an under-tracked ledger can't over-delete) — but that reasoning is nowhere in the plan, and nothing pins it down as a regression test. This is also the crux of the Tech Debt Disposition table's question about whether splitting ownership tracking across two ledger classes risks the two disagreeing about what's "managed" — the split itself is the right call (different resource kinds: JSON keys vs. filesystem artifacts), but the consistency window between the two writes deserves an explicit test, not just an implicit assumption. **Remediation**: add one GWT test — "interrupted between settings-write and ledger-write, next run reconciles both without stale-deleting anything."

- **Story 1.3.1 — `fork_pin_extension.py`'s only tests are static (argument-shape inspection) and dry-run, with no test that dry-run's output matches what a real run would persist.** Task 1.3.1c inspects the typer app's declared options for any `approved`-writing path (good, cheap, catches the right class of bug for the no-approval-path guarantee) and Task 1.3.1d adds `--dry-run`. But nothing confirms the dry-run-computed manifest entry is the same one a real (non-dry-run) fork would write — if they drift, the no-approval-path guarantee could hold for the code path being tested while the actually-shipped code path diverges. **Remediation**: one test that mocks the `gh` subprocess calls and asserts dry-run's computed diff equals the manifest entry a real run persists.

## Nitpicks
- `ManifestEntry`'s `upstream_repo`/`upstream_commit` and `fork_repo`/`fork_commit` repeat the same repo+commit shape twice as four separate fields; a shared `SourceRef(repo, commit)` value object would cut the field count in half and pairs naturally with the shared-parser remediation above.
- `package_paths` (Task 1.1.1b) and `PiPackageLedger`'s separately-tracked observed artifact paths (Epic 2.2) aren't reconciled in the plan text — clarify whether one is "declared/reviewed at fork time" and the other "observed at runtime," so two similarly-shaped `id → path(s)` records don't get confused by a future maintainer.
- `sync_pi_settings()` ([`cli.py:248-280`](file:///home/tstapler/dotfiles/stapler-scripts/llm-sync/src/cli.py#L248-L280), currently 33 lines, one job: load → render → save) is about to gain manifest-gate verification (Task 1.2.1b), package-ledger persistence (Task 2.2.1b), and stale-prune handling (Task 2.2.1c) in the same phase. Still fine today as a Facade/orchestrator, but if Phase 3-5 add further gates, consider extracting a small pipeline object so each step stays independently testable instead of accumulating inline.
- The Pattern Decisions table's "Memento/Snapshot" label for `PiPackageLedger` is more formal than what's actually built (save/find_stale/prune over a JSON state file) — structurally it's a small Repository of ownership records, the same shape as `PiSettingsTarget`'s unlabeled `managedKeys` mechanism it's explicitly modeled on. No code change needed, just a label mismatch.
