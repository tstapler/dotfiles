## Blockers

- [ ] **B1. Placeholder dates are already on disk and the plan will read them back as camera anchors.** `fix-metadata --apply` has evidently already run across the drive despite every album showing `metadata_status=pending` in `album_mapping.json` (Counter: `{'pending': 628}`). Evidence: `exiftool -DateTimeOriginal` on `2021 random photos/01d7bb5982378bdfff9f96deea5f7d3b.jpg` returns `2021:01:01 12:00:05` with `Make=Canon`; the next file returns `12:00:10` (the 5 s x index offset); the same signature appears in 14 other sampled albums (`1962:01:01 12:03:40` on an LG Electronics file, `1973:01:01 12:00:10` on an Apple file, `1964:01:01 12:00:05` on `FB_IMG_1595081508758.jpg`). Story 3.4 classifies any real `DateTimeOriginal` as `Anchor`, `Confidence 0.98` (its AC even uses `Make="Canon"`), and ADR-007 / Story 8.4 say real EXIF is "never overwritten". Consequences: (a) every placeholder-stamped file becomes an Anchor, so `2021 random photos` becomes `UploadGate`-eligible ("every file is Anchor / Written", glossary) and the deny-list is the only thing left standing; (b) anchor registry (5.2), calibration (5.3) and hold-out (5.5) are fitted on fabricated truth; (c) the true original dates (and any pre-existing scan `ModifyDate`) were overwritten with `-overwrite_original`, so they are unrecoverable from the file. Neither plan nor pitfalls B3/B6 mentions this; Story 1.7a only hypothesises why statuses are `pending`. — Add a story before 3.4 (and before any anchor use): `placeholder_signature` detector (`YYYY:01:01 12:00:SS`, `SS` a multiple of 5 times file index, equal to the album's `inferred_date` plus k x offset, identical Create/Modify/Original) that downgrades such EXIF to non-anchor evidence with reason `legacy_placeholder`, plus a measurement query (count per album) recorded in the PR. Rewrite 3.4 AC so Make/Software do not rescue a placeholder-shaped date. Recover real dates from filename dates (`20210701_172927.mp4`), `XMP`/`IPTC`, or the owner's source scans where they exist.

## Concerns

- [ ] **C1. Deny-list for `2021 random photos` is thin.** Story 1.6 keys on `folder_name` string equality in `upload_cmd`, before `upload_album_to_gphotos`; the album's id is `9102dede1a50` (`album_mapping.json`, index 542, 9,161 media files) and is a better key. Other callers of `upload_album_to_gphotos`, a renamed folder, or `album_name` differing from `folder_name` bypass it. The currently running background uploader (`ps`: `cli.py upload ... --album-id 1961 wedding day ...`, one process per album driven by an outside loop) is old code in memory and cannot be gated; the plan says only "not planned around" and never confirms the driving loop excludes the 2021 album. `deny release` has no precondition that dates are resolved. — Key on id and folder name and normalised path; put the check inside `upload_album_to_gphotos`; make `deny release` require zero `Review`/`Conflict` decisions for the album plus an interactive confirm; record in the plan the outer loop's album list (or exclude the album by pre-seeding a `status="denied"` manifest-like entry that the running loop already respects: `cli.py:414` skips ids in `manifest.completed_albums`).

- [ ] **C2. exFAT write safety is opt-in and incomplete.** `--workdir` is optional (8.4 AC, ADR-007 item 5), so the default is in-place writes on exFAT (`mount` shows `type exfat`, `errors=remount-ro`). Journal holds tags only, no byte backup, and ADR-007 rejects `_original` ("double disk on USB"); a corrupted write leaves the only copy broken, and `undo` cannot repair it. In the workdir path the copy-back "verified by size+key" is itself an in-place overwrite on exFAT, not write-to-temp-and-rename. No test touches exFAT behaviour (all fixtures on local fs). Two partial-write leftovers already exist on the drive (`2021 random photos/20210701_172927.mp4_exiftool_tmp`, `1961 wedding day Barbara & Lawrence/img033.jpg_exiftool_tmp`; `find` over depth 2), so Story 2.4 will refuse to run on day one with `Run: gphotos-organizer recover`, a command not delivered until 8.3b (W6, after 2.4 in W4). — Detect fstype (`exfat|vfat|fuseblk`) and default to workdir mode there; copy back to `name.tmp` then rename and verify hash; keep a local sha256 of pre-write bytes in the journal; ship a minimal `recover --list` with 2.4; add a story note describing how the two existing leftovers are resolved.

- [ ] **C3. Re-upload and duplicate behaviour rests on INFERRED facts and a self-reported flag.** ADR-008 marks "changed bytes create a new item" INFERRED/UNVERIFIED; 9.6 builds on it. Gate passes when "Tyler marks an album `trashed`" with no audit confirming the old items are gone, so a mistaken mark yields two copies of every file (old wrong date plus new). rclone `copy` to `gphotos:album/<name>` after trashing: whether it reuses or duplicates the album is UNVERIFIED (pitfalls s6), not in the 9.1 spike. The requirements Risk Control says "upload only after audit passes" and the plan's own Risk Control repeats it, but Story 9.2 gates on decisions and deny-list only. — Add to 9.1: album re-use behaviour and same-bytes-after-trash behaviour on a throwaway album; make 9.6's gate require an `audit` pass showing zero remote items remain for the album; add the "audit passes" predicate (or state in 9.2 why it is dropped).

- [ ] **C4. Success Metric 1 is blind to the damage already done.** The 604 uploaded albums were uploaded from files carrying B1 placeholders, so their remote dates sit in the past (e.g. `1962-01-01`), not in the upload window; the 9.3 flag "outside the decision interval" compares against decisions that (per B1) are built from those same placeholders. The audit can therefore report `Suspicious: 0` while thousands of items are fabricated.
