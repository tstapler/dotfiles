## Blockers
- [ ] **Migration Plan / Rollback + Story 2.2, 4.5, 5.2, 8.3 (persistence boundaries)** - The plan contradicts itself about which state is derived and which is irreplaceable, and the stated rollback destroys irreplaceable state. Story 2.2 puts `write_journal`, `labels`, `constraints` and `anchors` in `DATA/pipeline.db` (AC lists all 12 tables). The Migration Plan then says "rollback = delete `DATA/pipeline.db` (all derived except `labels`, `constraints`, `review/decisions.jsonl`, which are separate files...)", and the Rollback procedure repeats "delete `DATA/pipeline.db`". In the plan's own design, `labels`/`constraints` are tables (4.4, 4.5) not separate files, `anchors` with `source=owner_album` is owner input, and `write_journal` is the only record that makes `undo --run` possible (ADR-007, Story 8.5). Following the documented rollback after any `--apply` run deletes the journal, leaving EXIF changes unrecoverable, which violates the requirements' Risk Control ("every write is reversible") and the C1/C2 invariants in `research/architecture.md` s10. It also means the single SQLite file mixes derived caches (evidence, decisions) with source-of-truth data (journal, labels, constraints, anchors), the aggregate-boundary mistake Lens 1 item 3 is meant to catch. **Remediation**: (a) classify tables in the plan as DERIVED (`files`, `evidence`, `decisions`, `faces`, `clusters`, `run_metrics`, `uploads_observed`) vs SOURCE-OF-TRUTH (`write_journal`, `labels`, `constraints`, `anchors`, owner overrides); (b) either put source-of-truth tables in a second DB (`DATA/state.db`, never deleted by rollback, backed up before each `--apply`) or mirror every journal row and label/constraint to an append-only JSONL under `DATA/journals/` (the `journals/` subdir already exists in Story 1.1b but nothing writes to it); (c) rewrite Rollback to "delete derived tables only / `pipeline.db` only after `undo` and backup"; (d) add an AC to Story 8.3 and 4.5 that deleting the derived DB preserves undo and labels.

## Concerns
- [ ] **Story 2.1 / 2.6 (`DecisionStatus`)** - `DecisionStatus` includes `Written` and `Reverted`, but Story 8.6 derives write state from journal rows and C1 says decisions are "derived and recomputable". A persisted `Written` on `decisions` is a second source of truth: re-running `fuse` can clobber it or leave it stale after `undo`, and `UploadGate` (Glossary) tests "Anchor / Written". Recommendation: keep `DecisionStatus` to fusion outcomes (Anchor / Eligible / Review / Conflict / UserOverride) and expose write state as a join over the journal (`WriteState`: NotWritten / Pending / Verified / Mismatch / Reverted); have the gate (9.2) test `status in {Anchor, UserOverride} or write_state == Verified`.
- [ ] **Tech Debt Disposition, `cli.py` "Extend as-is" + Story 10.5 `test_cli_size.py`** - cli.py is the named hotspot (inline stages, state mutation). The plan adds about 25 commands (`index`, `analyze`, `fuse`, `plan`, `undo`, `recover`, `people`, `anchors`, `review *`, `deny *`, `models *`, `audit`, `remediation`, `report`, `status`) to the same file and also edits existing bodies in 1.2b, 1.3b, 1.5c, 1.6b, 1.7, 7.1b, 8.6 and 9.2. The "no command body exceeds 40 lines" guard would fail today: measured whole-function lengths are `upload_cmd` 73, `review_cmd` 63, `fix_metadata_cmd` 59, `scan_cmd` 55, `update_album_cmd` 54, `infer_cmd` 43 (AST count of `cli.py`). No story refactors them. Also `upload_cmd` owns the quota-retry loop (see below). Recommendation: (a) split new commands into Typer sub-apps in separate modules (`cli_review.py`, `cli_audit.py`, `cli_people.py`, registered with `app.add_typer`) so `cli.py` stays a shell; (b) add a task in Epic 1 (before 1.6b and 1.7) moving `upload_cmd`/`fix_metadata_cmd` bodies into `pipeline/*_service.py`; (c) define the guard as "body lines excluding option declarations" and state it applies to new and touched commands, or schedule the refactor.
- [ ] **Story 1.8 (quota test)** - The AC says `upload_album_to_gphotos` "raises/handles `QuotaExceeded`, sleeps `seconds_until_quota_reset()`" and "returns a failure result rather than raising `UnboundLocalError`". In the code, `upload_album_to_gphotos` only raises `QuotaExceeded` (`uploader.py` after `_run_rclone`); the wait-and-retry `while True` loop and `ok` live in `cli.py upload_cmd`, where `ok` cannot be unbound because the loop only exits via `break` after assignment. Task 1.8a's "injectable clock/sleep seam" has nowhere to live without moving the loop. Recommendation: extract the retry loop into `pipeline/upload_gate.py` (or `uploader.upload_with_quota_retry(album, sleep=time.sleep, now=...)`), test that, and drop the `UnboundLocalError` AC or reframe it as "bounded retries return a failure result".
- [ ] **Story 1.2 (atomic writes)** - AC says "all JSON state writers use it" and cites "the three writers", but `write_text(json.dumps(...))` appears in `cli.py:85` (scan), `:274` (update-album), `:357`, `:435` and `uploader.py:80` (`save_manifest`): five sites. The grep AC (`write_text(json` returns zero) would catch this, but the task text and file list understate the work, and `uploader.py` is also edited by 1.8 in the same wave (W2). Recommendation: list all five sites in Task 1.2b; sequence 1.2 and 1.8 (both edit `uploader.py`) or merge them.
- [ ] **Dependency Visualization / wave table** - Waves contradict stated dependencies. (a) 9.2 "needs 8.4" but 9.2 is in W6 and 8.4 in W7. (b) E3 header says plugins "need 1.4, 2.1, 2.3, 2.5", but 3.1/3.2/3.4 are in W4 and 2.5 is W5. (c) Same-wave file collisions: W2 has 1.2, 1.3, 1.6, 7.1 all editing `cli.py`; 1.3a (`scanner.py` `GPHOTOS_EXIFTOOL`) and 1.4c (`scanner.py`) both edit `scanner.py`; 1.2 and 1.8 both edit `uploader.py`. The plan mentions an "integrator task" for `cli.py` but doesn't assign one. Recommendation: move 9.2 to W8; either move 3.x to W5 or drop the 2.5 dependency (their ACs call `analyze` directly, so the dependency is not needed); name an explicit integrator task per wave for `cli.py`/`models.py`/`scanner.py`/`uploader.py`.
- [ ] **Story 6.1, 7.3, 2.2c, dateparse vs `cli.py` PEP 723 block** - Core-runtime code uses Pillow (`print_cues`, `thumbs.py`, dHash in `dup_groups.py`) and probably numpy-free image math, but `cli.py`'s inline deps are `typer, loguru, rich, pydantic` only (`cli.py:2-10`). No task adds Pillow, and 4.2c only asserts ML packages are absent. Similarly `analyze_ml.py` imports `pipeline/store.py`/`contract.py`, so its PEP 723 block must carry the same `pydantic` (and any shared deps). Recommendation: add an explicit task (Story 1.1 or 6.1a) to extend `cli.py`'s deps with Pillow, and a dependency-parity test that `pipeline/` imports resolve in both `cli.py` and `analyze_ml.py` environments (import-isolation test in 4.2c covers one direction only).
- [ ] **Story 2.1 / Glossary (`Evidence`, `PartialDate`)** - Illegal states are representable. `Evidence` has `abstain: bool` plus nullable `value`, allowing `abstain=True` with a value or `abstain=False` with none; Story 2.1 enforces this only by a serialization example. `PartialDate` stores `earliest`, `latest`, `precision` and `is_placeholder` independently, so `precision=Day` with a multi-year interval, or `is_placeholder` on a Day-precision date, is constructible. Recommendation: model `Evidence = Observation | Abstention` (sum type, `match`-exhaustive; the plan already uses this idea for `DecisionStatus`), and make `PartialDate` construct-only via classmethods (`day()`, `month()`, `range()`) that derive bounds from precision, with a `__post_init__` invariant (`precision==Day` implies `earliest==latest`). Add parse-at-boundary note: `ReviewDecision`/`decisions.jsonl` lines and `plan.jsonl` should be parsed into typed objects at read (Story 7.1, 8.4), not passed as dicts.
- [ ] **Story 2.2b (schema up front)** - Migration `001_initial.sql` creates all 12 tables including `faces`, `clusters`, `labels`, `constraints`, `anchors` before their stories (4.3-5.2) design them, then Stories 4.3a and 5.2a add repositories for them. This invites schema churn and violates forward-only additive migrations in spirit (they will become 002+ edits or a 001 rewrite). The AC "`schema_version = 1`" with all tables also couples E2 to E4/E5. Recommendation: `001` creates only `files, evidence, decisions, write_journal, uploads_observed, run_metrics, schema_version`; each later epic ships its own numbered migration.
- [ ] **Story 2.2 / 4.2 (two writers, one SQLite file)** - `cli.py` (Python 3.14) and `analyze_ml.py` (3.12) write the same DB, plus `cli.py` may run concurrently with an overnight ML batch (the plan's own operating mode). WAL is stated, but busy timeout, single-writer rules and the schema-version check on ML start (ADR-004) are not in any AC. Recommendation: add ACs for `PRAGMA busy_timeout`, retry on `SQLITE_BUSY`, and `analyze_ml.py` refusing to start when `schema_version` differs from the code's expected version.
- [ ] **Story 3.3 (Adapter seam) test strategy** - The parity golden is captured "on 30 representative albums before the change", but the legacy `enrich_mapping_data` mutates `AlbumMapping` in place and depends on hardcoded events; the `event` plugin deliberately changes outputs (Month interval, abstain on year-only). So "parity" really means "legacy callable unchanged" plus "plugin output differs by design". The plan states both but not how drift is detected over time. Recommendation: say explicitly that `enrich_parity.json` pins legacy behavior only, and add a second golden (`event_plugin.json`) so plugin changes are reviewable; set a removal criterion (delete `infer`/`enrich_mapping_data` once Story 1.5c and 3.3 are done and fusion decides album dates) so the Adapter does not become permanent.
