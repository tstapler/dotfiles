# ADR-007: EXIF writes via plan/apply with a journal; one year-precision policy; no `-overwrite_original`

**Status**: Accepted; amended 2026-10-16 (adversarial review B1, B2, B4, C2) · **Plan**: Stories 1.3, 1.5, 1.9, 1.10, 1.11, 8.1-8.8

## Context
Current code runs exiftool with `-overwrite_original` and no journal (`metadata.py:105,159-160`), counts failed chunks as success (`:196-200`), and writes whatever date it is handed (`:171`); the `YYYY:01:01 12:00:00` placeholders originate in `ai_enrich.py:31,85` and `scanner.py:68`. The source drive is exFAT (`errors=remount-ro`), where a disconnect mid-write is the likeliest corruption cause (`research/pitfalls.md` s5, INFERRED).

Measured 2026-10-16 with `exiftool -r -T -fast2 -DateTimeOriginal` over the drive's jpg/jpeg/png (VERIFIED by the coordinator; 15,943 dated files in the latest run, 16,044 in an earlier one): 9,460 are dated January 1 of some year (placeholder candidates); 5,926 are NOT Jan 1 but carry a `12:MM:SS` time-of-day, and 3,162 of those are exactly `12:00:SS` with SS a multiple of 5, the legacy 5-second-offset signature. Jan 1 alone therefore under-detects. Not proven: that every signature-bearing file is a legacy placeholder (most probably are) or that any Jan-1 file at another time is one; those stay `Suspect` until corroborated or owner-confirmed. The original dates the legacy writer overwrote are not recoverable from the files.

## Decision
1. **Plan/apply split**: `plan` writes `plan.jsonl` (old value, new value, confidence, provenance, plan hash); `fix-metadata --apply` consumes it and refuses a stale plan.
2. **Journal-first, in the source-of-truth store**: read `ExifSnapshot`, commit a `Pending` row to `state.db` `write_journal` (mirrored to `journals/<run_id>.jsonl`), write with `-P` and without `-overwrite_original`, read back, then `Verified` or `Mismatch` (album halts). The journal captures more than tags: pre-write `sha256`, size, `mtime_ns`, `ContentKey`, exiftool version, plan hash and the exact tag arguments. `undo --run` replays old values and deletes tags that were absent, from `state.db` or the JSONL mirror alone, and never depends on `pipeline.db` (ADR-002). Journal-only (no `_original` copies) so listings and rclone filters stay clean.
3. **Legacy destructive writer is locked until this ADR is implemented**: from Story 1.11 (wave 2) `fix-metadata --apply` exits 1; dry run still works. Story 8.4 removes the lock by replacing the path.
4. **Existing dates are classified before they are trusted** (Story 1.9): Genuine / Suspect / LegacyPlaceholder from five independent signals: (a) time-of-day `12:00:00 + 5k s`, (b) Jan 1, (c) absent `Make`/`Model`, (d) date equals the year/date parsed from folder or filename, (e) a monotone 5-second ladder across the files of one folder. A lone signal is `Suspect`, never `Genuine`; "not Jan 1" never implies `Genuine`; `LegacyPlaceholder` needs two strong signals (a, b, e) or one strong plus (c) and (d) (truth table in Story 1.9). Only `Genuine` (including owner `confirm-genuine`, which also works on `LegacyPlaceholder` with typed confirmation) is anchor-eligible. A one-time journaled revert (Story 8.7) applies to `LegacyPlaceholder` only; `Suspect` files go to review; quarantine alone is also acceptable and the owner chooses.
5. **Year-precision policy (single rule, stated identically in the plan glossary, Story 1.5 and Story 8.4; the owner can veto rule 3)**. For any decision coarser than Day (Year, Range, Decade, and Month):
   1. Never write a fabricated month/day into `DateTimeOriginal` or `CreateDate` by default.
   2. Record the known part in the file: keyword `gpo-year:<YYYY>` in XMP `dc:Subject` / IPTC Keywords. The file is listed in the review list as `source=year-precision`, and the upload gate holds it.
   3. Only if the owner releases an album with `--allow-year-precision` (needed solely if Story 9.1 confirms that an upload without an EXIF date lands on the upload date, which is the failure this project exists to prevent), write a mid-period noon date (July 1 12:00:00 for Year; the 15th at 12:00:00 for Month; July 1 12:00:00 of the midpoint year, floor((earliest+latest)/2), for Range and Decade), set `OffsetTimeOriginal` explicitly, add the marker keyword `gpo-date-inferred:<precision>`, journal the write, and keep the file visible in the review list. If the owner vetoes rule 3, year-precision files simply stay un-uploaded.
   This supersedes the previous "write July 1 noon for Year precision" default, which re-created defect B5 one level down.
6. **Tag policy for Day precision**: `DateTimeOriginal`, `CreateDate`, XMP `xmp:CreateDate` consistently; keep the scan date in the journal; `OffsetTimeOriginal` set explicitly to avoid timezone day shifts. PNG: XMP only. HEIC: only if the round-trip fixture passes. RAW: never written.
7. **exFAT safety is mandatory, not opt-in**: when the source filesystem type is `exfat`, `vfat` or `fuseblk` (read from `/proc/self/mountinfo`), `--workdir` is required and in-place writes are refused with no bypass flag. Flow: copy to the local workdir, journal the pre-write `sha256`, write, read back, copy back to `<name>.tmp` beside the original, verify the hash, then rename over the original (write-temp-then-rename; never an in-place overwrite of the only copy). `apply` refuses to start with `*_exiftool_tmp`/`*_original` leftovers present; `recover --list` (Story 1.10) exists before `index` so the instruction is actionable.

8. **Anchors and overrides get their date written** (consistency review B1): `plan` writes the decision date for every `Anchor` (filename, owner-album) and `UserOverride` whose on-disk date is not already a backed `Genuine` date; the upload gate passes a file only after a `Verified` write, or for a `source=exif` anchor whose on-disk `Genuine` date equals the decision (Stories 8.4, 8.6, 9.2).
9. **The journal restores tags, not damaged files, so real runs need a second line of defense** (pre-mortem failure mode 1): a verified full-drive backup on a different medium (the drive has 4.0G free of 58G), a 20-file canary, `fsck.exfat -n` before and every N albums, one album per mount-sync-verify cycle, local pre-write byte snapshots, and the SQLite backup API for `state.db` (Stories 8.3, 8.4, 8.8). The exFAT yank behavior is measured on a throwaway USB stick (Task 1.10c) rather than inferred.

## Consequences
Statuses derive from journal rows (`WriteState`, Story 8.6), so `metadata_status` cannot lie. Costs: a plan step, a second SQLite file, and slower exFAT writes (local copy plus copy-back). Year-only albums are not uploaded until the owner decides; this trades throughput for never placing a fabricated timestamp on the timeline.

## Alternatives rejected
`_original` backups (double disk on USB, accumulate); in-place overwrite (unrecoverable); sidecar-only (Google Photos does not read `.xmp` sidecars on upload, UNVERIFIED); always writing a mid-year noon date for year-precision decisions (indistinguishable from a real timestamp on the timeline, the previous default); a single `--overwrite_original` with `_original` retention (doubles disk on the exFAT drive).
