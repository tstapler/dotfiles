## 2. Age estimation and appearance cues

- Public age estimators (e.g. DEX, MiVOLO, InsightFace `genderage`) train on web photos (IMDB-WIKI, UTKFace, MORPH). Error is lowest for children and roughly flat-to-high for adults; adults 30-60 look similar across a 20-year window, so MAE of several years is typical (INFERRED from the literature; published MAEs not re-checked here). The requirements' own targets (±2 children, ±8 adults) are plausible but UNVERIFIED on this collection.
- Domain shift: scanned prints, B&W, faded color, halftone/scan artifacts, flash red-eye, small faces in group shots. Models see "old-looking skin" from fade/grain and bias older; B&W removes color cues the model may rely on. INFERRED; measure on the anchor set, stratified by color/B&W and decade.
- Regression to the mean: estimators shrink toward the training-set mean age (~30-40), overestimating children's ages less but underestimating the elderly. Do not use raw age for old subjects.
- Date = capture_year = birth_year + age, so error in age maps 1:1 into date error; uncertainty must be a distribution (sigma per age bracket), not a point. Fuse via likelihood over years, clamp to `[birth_year, folder_year_upper_bound, scan_date]`.
- Group photos: use the person with the smallest sigma (a child) not the mean of faces; wrong identity assignment breaks this.
- Photo-of-a-photo and portraits of the dead/old photos hung on walls: faces from the wrong era. Sanity guard: any person cluster with age>100 or <0 implied by fusion is rejected.
- Era-by-appearance (CLIP zero-shot) overlaps 1990-2005 per the requirements; treat as a weak prior only.
- Fusion must degrade gracefully: if sigma > threshold, output "unknown" and route to review list. Calibrate: report reliability (predicted vs actual coverage) per decade; a model that is overconfident will pass the threshold gate wrongly.

## 3. Face embeddings and clustering

- Drift: same person 20 vs 60 years apart can fall below the same-identity threshold; clusters split per era. Reverse risk: siblings/parents/children look alike, so a loose threshold merges family members. Decades of drift and kinship are in tension; no single threshold works. Design: conservative threshold, per-era sub-clusters, manual merge with a persistent "same-person" / "cannot-link" constraint store (human labels override the algorithm on rerun).
- Poor-quality crops (small, blurred, profile, B&W) produce unstable embeddings. Filter by detection score and face size; keep quality score with the embedding; exclude low-quality from centroid computation.
- Non-determinism: HDBSCAN/agglomerative are order-sensitive on ties; DBSCAN depends on point order; UMAP/k-means are seeded. Pin seeds, sort inputs by file hash, version the cluster run, and persist human labels keyed by face id (file hash + bbox), not by cluster index (indices change between runs).
- Cache invalidation: key by `(sha256 of file bytes, model name+version, detector params, preprocessing)`. Rewriting EXIF changes the file hash even though pixels are unchanged. So hash the pixel data or hash before any write and store the mapping; otherwise every exiftool write invalidates the whole cache. Store a model version in every cache row and invalidate on change.
- Biometric/privacy: embeddings are biometric identifiers of family members (including the dead and children). Store only on local disk under `~/.local/share/` or `~/.cache/`, not under `~/dotfiles`; add the path and `*.sqlite`/`*.npy` to `.gitignore` (repo root `.gitignore` was checked only at head; add explicit entries). Create files `chmod 600`, directory 700. Consider full-disk encryption note. Do not send crops to a cloud plugin unless `--allow-cloud` is set per run and log what was sent. Redact names in logs/report committed to git; `project_plans/` is in git, so reports with names/ages must stay out of it.
- Also keep the dotfiles repo clean: current git status shows `project_plans/gphotos-organizer-pipeline/` untracked, so avoid putting data there.
- Licensing: InsightFace says "ALL models are available for non-commercial research purposes only" (VERIFIED, https://github.com/deepinsight/insightface/tree/master/model_zoo). Fine for personal use, but note if this is ever published. The code is MIT-style; weights are the restricted part. Alternatives with permissive weights: check before adoption (UNVERIFIED). dlib `face_recognition` models are public domain/Boost-licensed (INFERRED).
- Download/size: buffalo_l pack is ~280 MB (INFERRED). Download on first use into a model cache dir, verify checksum, fail clearly offline. Do not vendor in git.
- CPU runtime: ONNX Runtime on CPU, detection (SCRFD) ~50-200 ms/image and recognition ~20-100 ms/face on a desktop CPU (INFERRED; benchmark on this machine before committing). 17k images x ~0.3-1 s = 1.5-5 h single-threaded; fine for overnight but only with a per-file cache. Large scans (tens of MP) dominate decode time: downscale to ~1600 px longest side before detection; this also lowers small-face recall, so tune.
- Memory: batch and process-pool per file, not per album; ONNX sessions are not fork-safe if created before the fork.

## 4. Cloud vision / LLM guesses

- Confirmation bias: a prompt that includes the folder name, nearby photos' dates, or "this is probably 1975" makes the model agree. Provide the image only (plus neutral instruction), ask for features observed (clothing, film stock, vehicle models, signage) and a year range, and score independently from other votes.
- LLMs state specific years with high confidence from weak cues; treat output as a range with low weight, and calibrate against anchors. Re-sampling at temperature>0 gives different answers: cache the first answer per `(file hash, model, prompt version)`.
- Cost and privacy: a per-run `--allow-cloud` flag, a sample cap, a spend cap, and a log of what was uploaded. Images of identifiable family members leave the machine; Tyler decided this is opt-in (requirements).
- Votes from correlated sources (same face model in age and era plugins; folder-year and filename-year both derived from the album) are not independent. Naive Bayes fusion double-counts; group correlated plugins or discount.

## 5. exiftool write hazards

- In-place vs backup: by default exiftool writes a temp copy and renames, keeping `FILE_original`. `-overwrite_original` removes this safety; `-overwrite_original_in_place` rewrites the same inode (preserves hard links/ownership but is not atomic and a crash can corrupt the file). (exiftool docs, https://exiftool.org/exiftool_pod.html, INFERRED/not re-fetched.)
- Leftover temp files: a killed run leaves `*_exiftool_tmp` beside the original (seen earlier per task brief). Before each run, glob for `*_exiftool_tmp` and `*_original`, report, and refuse to proceed (or clean up after confirming the original is intact). Treat their presence as proof of a partial write for that file.
- FAT/exFAT USB drive (`/run/media/tstapler/EE5B-3D9B`, listed OK this session): exFAT has 2-second mtime granularity on FAT and no Unix permissions; rename-over-existing can fail if the drive is yanked; the safe-rename flow needs free space equal to the file size per file in flight; a drive disconnect mid-write is the likeliest corruption cause. INFERRED. Mitigation: copy to a local working dir, write there, verify by read-back, then copy back (or write sidecars only), and `sync` before unmounting. Case-insensitive names: `IMG.jpg` and `img.JPG` collide; `_original` suffix files double the file count in listings and will be picked up by the scanner and the rclone `--include "*.jpg"` filters (VERIFIED the upload cmd includes only extension filters, `uploader.py:98-102`: `foo.jpg_original` does not end in `.jpg`, so it is excluded; INFERRED for `-overwrite_original` absent).
- mtime: exiftool changes the file mtime unless `-P` is passed. Google Photos shows EXIF date first (below), but the scanner/anything keyed on mtime and your own change detection will be disturbed. Use `-P`, or key all caches on content hash.
- Tag precedence: Photos readers prefer EXIF `DateTimeOriginal`, then `CreateDate`, and then XMP `photoshop:DateCreated`/`xmp:CreateDate` in various orders; conflicting values between EXIF and XMP cause inconsistent results across tools (INFERRED). Write EXIF `DateTimeOriginal` + `CreateDate` + XMP `xmp:CreateDate` consistently, or only EXIF; and also fix IPTC `DateCreated` if present (stale IPTC date is a classic override). Scans often have a *scan* date in `CreateDate`/`ModifyDate`/`FileModifyDate`; the current code overwrites `ModifyDate` with the inferred date, losing the digitization date (keep it in a journal).
- Time zone: EXIF has no zone; `OffsetTimeOriginal` absent. Google Photos then assumes the viewer/upload tz, so `12:00:00` placeholder may show as the previous/next day; a day-level shift is cosmetic but visible in the timeline sort. INFERRED.
- Format hazards: JPEG fine. PNG/GIF/BMP/WebP have limited or no EXIF (exiftool writes XMP or fails; Google Photos reading it is UNVERIFIED). HEIC: exiftool can write EXIF/XMP to HEIC, but it can corrupt Apple Live Photo/HEIF sequences in edge cases and exiftool docs flag HEIC writing as limited (INFERRED; test). TIFF: writing grows the file; RAW: exiftool may write to the RAW file itself (never do; use XMP sidecar). Video (MP4/MOV): QuickTime atoms `CreateDate/ModifyDate/MediaCreateDate/TrackCreateDate` are UTC by spec; QuickTime epoch is 1904, and Google Photos uses `CreateDate` (INFERRED). Dates <1970 for scans: EXIF supports 1900+; `FileModifyDate` cannot be set before 1970 on some filesystems, and the exFAT epoch is 1980 (INFERRED).
- Sidecar vs embedded: Google Photos does not read `.xmp` sidecars on upload (INFERRED, UNVERIFIED), so sidecars are useful for the journal/review but do not fix the timeline. Embedded write is required for upload.
- Partial failure: exiftool returns 0 on "minor" warnings; `-ignoreMinorErrors` (used in `metadata.py:187`) suppresses even warnings that mean a tag was not written. Verify by re-reading tags (`-json -DateTimeOriginal`) after write and compare.
- Concurrency: don't run two exiftool processes on the same file; don't run rclone while writing (the uploader reads while metadata writer replaces files).
- Journal: record `{path, sha256_before, sha256_after, tag: old_value, new_value, ts}` before write, so revert is `exiftool -tag=old`. A byte-exact restore requires the `_original`; the journal restores only tags. Choose one explicitly. For irreplaceable family scans, keep exiftool's `_original` backups on local disk, not on the FAT drive.

## 6. Google Photos behaviours

- Displayed date: rclone docs say item dates are "the EXIF creation date (or upload date) and can't be changed" (VERIFIED, https://rclone.org/googlephotos/). File mtime is not used (INFERRED: consistent with that statement; rclone does not set it). Files with no EXIF date therefore get the upload date, which is the "photos show as today" symptom. Placeholder `YYYY:01:01 12:00:00` removes that symptom but fabricates a date (B5).
- Cannot edit dates or delete via API/rclone: rclone docs say deletion "only works under `album`" and deleted media is not permanently removed; albums cannot be deleted; rclone "can only upload to, and remove files from, albums it created" (VERIFIED, same page). The official Library API overview page lists no date-edit or media-delete method and says some scopes were removed on April 1 2025 (VERIFIED partially, https://developers.google.com/photos/library/guides/overview; the details page was not fetched). Hence "no API route to fix an uploaded item's date" is VERIFIED only as "not documented"; a negative claim for the full API reference (REST `mediaItems` methods: get, list/search, batchCreate, batchGet; no patch for creationTime) is INFERRED. Remediation is the web UI "Edit date & time" or trash + re-upload.
- Read limits since 2025: rclone docs: "Since March 31, 2025, rclone can only download photos it uploaded" (VERIFIED). So an audit that lists *all* remote items by date might see only rclone-uploaded items. This is acceptable here (everything was uploaded by rclone) but items uploaded by other means (phone) are invisible; the audit's coverage claim must be scoped. The listing returns dates? UNVERIFIED: test `rclone lsjson gphotos:media/by-day` or `gphotos:media/all --fast-list` to confirm `ModTime` equals the photo's creation time.
- Dedup: Google dedups uploads by content hash (INFERRED/widely reported, UNVERIFIED in official docs). rclone docs: "Identical uploads keep the filename from the first upload" (VERIFIED), consistent with this. Consequence: re-uploading a file after an EXIF edit changes bytes, so it is a new item (two copies: old wrong-date, new right-date); re-uploading unchanged bytes is a no-op and will NOT fix the date. Trash the wrong copy first in the web UI; trash then re-upload of the same bytes may be blocked while the item is in trash (UNVERIFIED). Edited-bytes check: confirm that exiftool-modified files hash differently (they do, since metadata is part of the file).
- Original quality: uploaded at original quality and counts against storage (VERIFIED); no "storage saver" through the API. 17k photos can exhaust the 15 GB free tier; estimate total size before upload.
- rclone `copy` to `gphotos:album/<name>`: albums are created by rclone (so addable), but re-running creates same-named albums? Behavior UNVERIFIED; rclone docs say duplicate names get an ID suffix (VERIFIED for files; albums UNVERIFIED). Album-name collisions between folders: check `album_name` uniqueness in `album_mapping.json`.
- Quota: the page fetched does not mention 429 (VERIFIED absence); the Library API has per-project daily request quota and a ~10,000 requests/day documented for upload/media access (INFERRED; check https://developers.google.com/photos/library/guides/api-limits-quotas). rclone retries internally and may exit 0 after giving up on some files, so text scanning (`uploader.py:29`) is reasonable but fragile; confirm by checking per-album remote counts after upload (the audit). The shared rclone client_id is "being retired in 2026" (VERIFIED, rclone page): create your own client_id or uploads will break/throttle together; an own client in "testing" mode has refresh tokens that expire after 7 days (INFERRED).
- Non-photo files: non-media files upload then fail (VERIFIED); the `--include` list guards this.
- Image processing: HEIC/RAW/uncommon formats may be accepted but rendered differently; videos > some size are slow (INFERRED).

## 7. Plugin framework over-engineering

- Requirements already flag this. For 3-5 plugins in a PEP 723 script: a plain registry (`dict[str, Plugin]` populated by explicit imports or a `plugins/` directory scan with `importlib`) is enough. Entry points need an installed package, which conflicts with a `uv run` single-file CLI (INFERRED). No dependency-injection container, no versioned plugin API, no dynamic reloading.
- Keep the interface to one method: `analyze(image_path, context) -> list[Vote]` where `Vote = {year_lo, year_hi, confidence, provenance}`; cache keyed by `(file_hash, plugin_name, plugin_version)`; plugins declare their own heavy deps lazily (so the CLI starts fast and `uv` env does not need onnxruntime for fix-metadata).
- Heavy dependencies: InsightFace + onnxruntime + numpy in PEP 723 inline deps make every `uv run` resolve/install on first run; put heavy plugins in a separate optional dependency group.
- Tests: repo style is plain functions (no pytest); keep plugin tests deterministic by using synthetic embeddings, not real model weights.

## 8. Cross-cutting design rules (what must be designed against)

1. Never write a date that is not backed by a vote with provenance; placeholders go to the review list, not EXIF.
2. Journal every write; read back after write; status derives from read-back, not exit codes.
3. Upload gate: only albums with all files `date_resolved`; run the audit after each album; manifest is advisory.
4. Local working copy for the exFAT drive; refuse to run if `*_exiftool_tmp` or `_original` leftovers exist unreviewed.
5. Cache by pixel/content hash captured before any write; include model + prompt + params version.
6. Human labels (identity, same/cannot-link, birth dates) are stored separately from derived data, keyed by stable face id, and never overwritten by reruns.
7. Embeddings, crops, and reports with names stay out of git (gitignore + outside the repo).
8. Calibrate per decade and per color/B&W against anchors, report reliability; if not calibrated, the plugin's vote weight is capped.
