# llm-sync: confirm Antigravity commands-as-skills preserves $ARGUMENTS/explicit-invocation semantics (Priority 3 | Status: in_progress)

## Description
## Problem

Per `stapler-scripts/llm-sync/AGENTS.md`:

> **Skills:** `~/.gemini/config/skills//SKILL.md` (Note: commands sync as skills here)

`AntigravityTarget.save_commands()` in `stapler-scripts/llm-sync/src/targets/gemini.py` (~line 267) writes every Claude command (`.claude/commands/.md`) into the Antigravity skills directory as a `SKILL.md`, dropping the command's original invocation model. Claude commands are explicitly invoked (`/command some args`, with `$ARGUMENTS` substitution); Antigravity skills are typically auto-triggered by the model deciding relevance, not explicitly invoked with positional arguments the same way.

This is flagged as a documented, deliberate choice, not obviously a bug — but it's an open UX-parity question: for commands that rely on `$ARGUMENTS` (e.g. anything taking a target file, PR number, or search query as an argument), does the synced Antigravity skill still work, or does it silently lose the ability to receive arguments at invocation time?

## Suggested action
- Manually test a `$ARGUMENTS`-using command (e.g. something under `.claude/commands/`) synced to Antigravity and confirm whether argument passing still works via whatever invocation UI Antigravity skills support.
- If it doesn't: document the limitation explicitly (which commands are safe to sync this way vs. which lose functionality), or investigate whether Antigravity has a more command-like invocation primitive to target instead of skills.
